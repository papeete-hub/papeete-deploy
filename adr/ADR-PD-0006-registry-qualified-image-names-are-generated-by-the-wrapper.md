# ADR-PD-0006 — Registry-qualified image names are generated, not authored

## Context

An actor's base manifest names its container by the actor's own normalized name and nothing else —
`bnk.rlvr.cap.sup.002.ben-implementation`, no host, no tag (`papeete-actor`'s `ADR-PA-0025`). Until
now the wrapper kustomization supplied only the missing half of that: `newTag`, the version
resolved against a registry. That is sufficient exactly while images live in the local Docker
daemon's own store, where an unqualified name already resolves.

It stops being sufficient the moment images are built somewhere other than where they run. An
actor that builds an image in-cluster and a Pod that runs it are different pods, possibly in
different namespaces, so the image travels through a registry — and then the manifest needs to say
`<registry>/<repository>/<name>:<tag>`, not `<name>:<tag>`.

`AcrRegistry` already had a `repository_prefix` constructor parameter for its own tag listings.
Nothing ever passed it.

## Decision

**`newName` is generated by the wrapper kustomization, alongside `newTag`.** The image entry
becomes `{name, newName, newTag}` when the registry in play qualifies its images, and stays
`{name, newTag}` when it does not. `Registry` gains `image_name(name) -> str | None` for that:
`LocalDockerRegistry` returns `None`, `AcrRegistry` returns
`<acr>.azurecr.io/<prefix>/<normalized name>`.

**An actor's repository path is the product's own name**, normalized — `foundry`, taken from
`product.yaml`'s `product:` field by `_registry_from_args()`. Not a flag, and not a new field in
the product contract.

## Rationale

**Because `ADR-PD-0005` already settled this argument.** Welding a registry host into an actor's
own base manifest makes that manifest deployable to exactly one environment — the same failure as
hand-typing an ingress path prefix, and the wrap-never-edit discipline exists to prevent it. An
actor is authored once and deployed to many environments; which registry a given environment pulls
from is the deployer's knowledge, and `ADR-PD-0001` already names this package as the one allowed
to hold it.

**The prefix is derived, not declared, because it is not a separate choice.** A product's actors
belong in that product's repository path by definition; a flag would only create the opportunity
for the two to disagree. Deriving it also means `papeete-product`'s contract is untouched — no new
field, nothing for a product author to get wrong.

**One change serves both callers.** `k8s.apply()` threads the parameter through, and
`BNK.RLVR.CAP.SUP.002.BEN-task-orchestration` imports `papeete_deploy.k8s` directly rather than
going through `deploy()`, so it inherits this without a second code path.

## Consequences

- **Nothing changes for `--registry local`.** `image_name()` returns `None`, no `newName` is
  emitted, and the rendered manifest is byte-identical to before.
- **`AcrRegistry` is now partly exercised.** `image_name()` is pure string composition and is
  covered offline; `list_tags()` still needs a live registry to mean anything and remains
  uncovered, as `ADR-PD-0001` recorded.
- **A namespace still needs its own pull Secret.** This decision qualifies the image name; it does
  not authenticate the pull. Whoever creates a namespace creates its `imagePullSecrets` —
  `papeete-platform`'s `examples/acr-local` for a long-lived one, the deploying actor for an
  ephemeral one.
- **Components are not covered by this.** Only actors — the images this package resolves from a
  `product.yaml` — take the product prefix. An image an actor builds for its own capability is
  named by that actor and never resolved here.
